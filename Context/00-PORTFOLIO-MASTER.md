# 00 — Master portfolio specification

Status: E strategy + P implementation baseline + V publication facts. See [status definitions](README.md).

## Purpose and identity — E

**IB Dev Studio — Ibrahim Bangura** presents a junior full-stack developer with UI/UX, frontend, WordPress and database-backed application experience. The recorded positioning is:

> Junior Full-Stack Developer | UI/UX, React, WordPress & REST API Integration

The site should win freelance, contract, part-time and junior opportunities while supporting internships and professional credibility. Organize it around what Ibrahim can help people accomplish; technologies provide supporting proof. Agentic AI and workflow experience is a secondary differentiator.

The desired visual character is minimal, modern, technical, professional, clean, spacious and trustworthy. The established color direction is deep navy/dark blue, electric blue, charcoal and white, with optional restrained green. No exact colors, typefaces or tokens were locked.

## Scope — E foundations, P release boundary

The content foundations are Home, About, Services, Work/Projects, Skills and Contact, with case studies for substantial projects. Navigation and page distribution were not final.

P release: a homepage, work index, reusable project detail, about page, services page and contact page. Skills live in About and a compact homepage section. Launch with only evidence-ready projects; build toward 4–6 featured projects rather than padding the selection. No blog, account system, ecommerce, CMS or portfolio database is necessary for v1.

## Visitor journeys — P

A client sees the offer → finds relevant work → reads scope and contribution → contacts Ibrahim with a project brief. A recruiter sees the junior role → assesses a case study → opens the corresponding repository → checks background and contacts Ibrahim.

## Acceptance criteria — P

- Identity and junior level are visible without opening the biography.
- UI/UX, React/Tailwind, broad WordPress services and database-backed applications are represented.
- Every published project has a correct origin label, explicit role, realistic maturity and evidence.
- No invented employment, testimonials, client logos, revenue, user counts or efficiency claims.
- Main navigation, project links and contact route work on mobile and keyboard.
- Token definitions, accessible states and responsive layouts follow 03–04.
- Case studies and GitHub descriptions agree on features and contribution.
- No unresolved placeholders or draft projects appear in the published site.
- Build, link, accessibility and responsive checks in 07 pass.

## Delivery sequence — P

1. Audit projects and collect publication facts using 05.
2. Complete the strongest case studies with 06 and matching GitHub packs.
3. Review draft copy, navigation and proposed design tokens.
4. Build accessible static layouts and reusable components.
5. Add essential interactions and evaluate performance.
6. Check facts, devices, links and metadata; deploy only under the implementation task's authorization.
